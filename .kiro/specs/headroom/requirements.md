# Requirements Document

## Introduction

Headroom is a static, serverless web tool built for the Torus "Compute Follows the Sun" (Option 2) bounty at Hard Tech Week, Salt Lake City. The tool models a simulated 10 MW AI cluster in PacifiCorp East (EIA code `PACE`) and decides, for every flexible job in every time slot, where the job's electricity comes from: the grid now, on-site storage (battery + flywheel) now, later (defer), or another region. The tool then shows how much grid capacity the site frees up for the utility.

All numbers are precomputed in Python at build time from real EIA-930 grid data and a labeled simulated site model, written to static JSON, and served through Amazon S3 + Amazon CloudFront defined in AWS CDK v2 (TypeScript). The page loads data once and makes zero network calls afterwards, so the demo survives a venue Wi-Fi outage.

The story every requirement serves: the AI site becomes a flexible grid asset instead of a grid problem.

Source of truth: `AGENT_BRIEF_HEADROOM.md`. Schedule: feature freeze Tuesday Oct 27, 2026, 10 PM MT; demo Wednesday Oct 28, 2026.

## Glossary

- **Headroom_System**: The complete project: simulation, web app, infrastructure, scripts, and documentation in the `headroom` repository.
- **Developer**: The person or agent building, deploying, and maintaining the Headroom_System.
- **Site_Stack**: The single AWS CDK v2 stack named `HeadroomSiteStack`, defined in `infra/lib/site-stack.ts`.
- **Site_Bucket**: The private Amazon S3 bucket created by the Site_Stack that stores the built web files.
- **Distribution**: The Amazon CloudFront distribution created by the Site_Stack that serves the Site_Bucket contents.
- **Site_URL**: The public URL `https://<distributionDomainName>` of the Distribution.
- **Deploy_Script**: `scripts/deploy.ps1`, the PowerShell script that builds and deploys the Headroom_System.
- **Smoke_Script**: `scripts/smoke.ps1`, the PowerShell script that checks the live Site_URL after deployment.
- **CI_Pipeline**: The GitHub Actions workflow at `.github/workflows/ci.yml`.
- **EIA_API_KEY**: The free EIA Open Data API key, stored locally in `.env` as `EIA_API_KEY=...`.
- **Secret_Grep**: A search of every file under `web/dist` for the value of EIA_API_KEY.
- **EIA_Fetcher**: `sim/fetch_eia.py`, the module that downloads EIA-930 data through EIA API v2.
- **Raw_Cache**: The `data/raw/` directory holding unmodified EIA API responses, committed to git.
- **Region_Data**: EIA-930 hourly balancing-authority series of type `D` (demand), `DF` (day-ahead demand forecast), `NG` (net generation), and `TI` (total interchange).
- **Fuel_Mix_Data**: EIA-930 hourly net generation by fuel type for a balancing authority.
- **Data_Range**: 2026-06-01T00:00Z through 2026-09-30T23:00Z, inclusive.
- **Known_Fuel_Codes**: The EIA fuel codes `COL`, `NG`, `NUC`, `OIL`, `OTH`, `SUN`, `WAT`, `WND`.
- **Carbon_Calculator**: `sim/carbon.py`, the module that computes hourly average carbon intensity.
- **Carbon_Intensity**: Generation-weighted average lifecycle emissions of a region's fuel mix for one hour, in gCO₂eq/kWh.
- **Emission_Factor_Table**: The per-fuel lifecycle emission factors in gCO₂eq/kWh: Coal 820, Natural gas 490, Biomass 230, Solar 48, Hydro 24, Nuclear 12, Wind 11, Geothermal 38 (IPCC AR5 medians, REAL); Oil 650 and Other 300 (ILLUSTRATIVE).
- **Scenario_Selector**: The logic that picks scenario windows from the PACE data.
- **Scenario**: One 48-hour analysis window; either `peak` or `sun`.
- **Peak_Scenario**: The 48-hour window centered on the highest PACE demand hour in the Data_Range.
- **Sun_Scenario**: The 48-hour window in the Data_Range with the highest PACE solar share.
- **Solar_Share**: PACE `SUN` net generation divided by PACE total net generation from Fuel_Mix_Data, summed over a window.
- **Config_Module**: `sim/config.py`, the single module that holds every simulation constant.
- **REAL**: A label meaning a value comes from a cited public source.
- **ILLUSTRATIVE**: A label meaning a value is a plausible assumption chosen for the demo, not a measured or published value for this site.
- **SIMULATED**: A label meaning data is generated by the Headroom_System's models.
- **Site_Model**: `sim/site.py`, the simulated AI facility, including loads, Battery, and Flywheel.
- **IT_Peak**: The facility's peak IT load, 10 MW.
- **PUE**: Power usage effectiveness, 1.3; facility power equals IT power multiplied by PUE.
- **Inference_Load**: The non-flexible inference share of IT load.
- **Training_Job**: A synthetic flexible training workload with an id, arrival time, power (kW), duration, and deadline.
- **Job_Generator**: `sim/jobs.py`, the module that creates Training_Jobs.
- **Restart_Penalty**: 5 minutes of extra run time added to a Training_Job each time the job resumes after a pause.
- **Battery**: The simulated on-site battery, 4 MW / 16 MWh, 90% round-trip efficiency.
- **Flywheel**: The simulated on-site flywheel, 2 MW / 0.5 MWh, 85% round-trip efficiency.
- **SOC**: State of charge of a storage device, as a percentage of energy capacity.
- **Tariff**: The ILLUSTRATIVE energy and demand pricing used for cost calculations.
- **On_Peak_Period**: Weekdays 15:00 to 20:00 America/Denver.
- **Slot**: One 15-minute time step of a Scenario; a Scenario has 192 Slots.
- **Site_Grid_Draw**: Power the site imports from the PACE grid in a Slot, in kW.
- **Stress_Slot**: A Slot whose PACE demand is within the top 5% of PACE demand values in the Scenario window.
- **DR_Event**: A simulated utility demand-response event requesting the site to shed load.
- **Requested_Shed**: The load reduction a DR_Event requests, default 4,000 kW for 2 hours.
- **Grid_Import_Cap**: Baseline Site_Grid_Draw at DR_Event start minus Requested_Shed, in kW.
- **Event_Zoom**: A 1-second-resolution series covering the first 600 seconds of a DR_Event.
- **Scheduler**: `sim/scheduler.py`, the module that implements both scheduling policies behind one interface.
- **Baseline_Policy**: The `baseline` policy: every Training_Job runs on arrival from the grid, with no storage.
- **Headroom_Policy**: The `headroom` policy: a rolling-horizon greedy scheduler with a 24-hour look-ahead.
- **Route**: One of `GRID_NOW`, `STORAGE_NOW`, `DEFER`, `MOVE_REGION`, assigned to a runnable Training_Job in a Slot.
- **Alternate_Region**: `BPAT` (Bonneville Power Administration) or `CISO` (California ISO).
- **Idle_Capacity**: SIMULATED spare GPU capacity in an Alternate_Region for one hour, between 0% and 30%.
- **Route_Cost**: Energy cost + demand-charge risk + carbon cost at the carbon shadow price + deadline-risk penalty.
- **Demand_Charge_Risk**: Increase in the window's peak 15-minute Site_Grid_Draw (kW) caused by a Route, multiplied by the demand charge ($/kW).
- **Reason_String**: A human-readable explanation attached to every Decision.
- **Decision**: A record of a Route assignment for a Training_Job, including time, job id, Route, target, and Reason_String.
- **Metrics_Calculator**: `sim/metrics.py`, the module that computes KPIs.
- **Scenario_Builder**: `sim/run_scenarios.py`, invoked as `python -m sim.run_scenarios`.
- **Scenario_File**: `web/public/scenarios/peak.json` or `web/public/scenarios/sun.json`.
- **Output_Contract**: The JSON schema for Scenario_Files defined in Requirement 16.
- **Type_Definitions**: `web/src/types.ts`, the TypeScript types for the Output_Contract.
- **Web_App**: The single-page Vite + React + TypeScript + Recharts + Tailwind application in `web/`.
- **Mode**: The Web_App's policy view: `Baseline` or `Headroom`.
- **KPI_Row**: The Web_App panel showing headroom kW returned, $ saved, CO₂ avoided, inference SLA, and training deadlines met.
- **Main_Chart**: The Web_App's 48-hour chart of site and grid series.
- **DR_Button**: The Web_App button labeled "Fire demand-response event".
- **Zoom_Panel**: The Web_App panel that plays back the Event_Zoom series.
- **Decision_Log**: The Web_App's scrolling feed of Decisions.
- **Footer**: The Web_App's always-visible bottom bar with data provenance and context.
- **Duke_Context_Line**: The statement: Duke Nicholas Institute, *Rethinking Load Growth* (Feb 2025): the largest US balancing areas could integrate about 76 GW of new load with 0.25% average annual curtailment.
- **Test_Suite**: The pytest tests in `sim/tests/`.
- **Decisions_File**: `DECISIONS.md`, the log of judgment calls made during the build.
- **README**: `README.md` at the repository root.

## Requirements

### Requirement 1: Static Hosting Infrastructure

**User Story:** As a Developer, I want a single CDK stack that hosts the site privately behind CloudFront, so that the demo has a public HTTPS URL with no servers to run.

#### Acceptance Criteria

1. THE Site_Stack SHALL be defined in AWS CDK v2 TypeScript as exactly one stack named `HeadroomSiteStack`, with the stack class in `infra/lib/site-stack.ts` and the app entry point in `infra/bin/headroom.ts`.
2. THE Site_Stack SHALL deploy to the AWS region read from a context value in `infra/cdk.json`, and the committed `infra/cdk.json` SHALL set that context value to `us-west-2`.
3. THE Site_Stack SHALL create the Site_Bucket with `BlockPublicAccess.BLOCK_ALL`, `enforceSSL: true`, S3-managed encryption, `removalPolicy: DESTROY`, and `autoDeleteObjects: true`.
4. THE Site_Stack SHALL connect the Distribution to the Site_Bucket only through `S3BucketOrigin.withOriginAccessControl(bucket)` from `aws-cdk-lib/aws-cloudfront-origins`, with no S3 static website hosting configuration and no bucket policy statement granting public read access on the Site_Bucket.
5. THE Site_Stack SHALL configure the Distribution with `defaultRootObject: 'index.html'`, `viewerProtocolPolicy: REDIRECT_TO_HTTPS`, `compress: true`, `cachePolicy: CACHING_OPTIMIZED`, `responseHeadersPolicy: SECURITY_HEADERS`, `priceClass: PRICE_CLASS_100`, and `httpVersion: HTTP2_AND_3`.
6. WHEN the Distribution receives a viewer request for which the origin returns HTTP 403 or HTTP 404 (including a request for a path with no matching object in the Site_Bucket), THE Distribution SHALL respond with the contents of `/index.html` and HTTP status 200.
7. THE Site_Stack SHALL include a `BucketDeployment` that uploads the contents of `../web/dist` (relative to `infra/`) to the Site_Bucket, with `distribution` set to the Distribution and `distributionPaths: ['/*']`.
8. WHEN an `npx cdk deploy` of the Site_Stack completes successfully, THE Distribution SHALL have received a cache invalidation for `/*` created by that deployment, so that every file in `web/dist` at deploy time is served at the same relative path under the Site_URL.
9. THE Site_Stack SHALL emit a `CfnOutput` named `SiteUrl` whose value is `https://` followed by the Distribution's CloudFront-assigned domain name.
10. THE Site_Stack SHALL tag every resource in the synthesized CloudFormation template that supports tags with the tag key `Project` and value `headroom`.
11. IF the installed `aws-cdk-lib` API names differ from the names in this requirement, THEN THE Developer SHALL use the equivalent installed API and add an entry to the Decisions_File naming the original API, the substituted API, and the reason.
12. WHERE a custom domain is configured and a Route 53 hosted zone for that domain already exists, THE Site_Stack SHALL attach to the Distribution an ACM certificate issued in `us-east-1`.
13. IF a client sends a request directly to the Site_Bucket's S3 object URL for any uploaded file, bypassing the Distribution, THEN THE Site_Bucket SHALL deny the request with HTTP status 403.
14. WHEN `npx cdk synth` is run in `infra/` without AWS credentials (as in the CI_Pipeline), THE Site_Stack SHALL synthesize a CloudFormation template and the command SHALL exit with status 0.
15. THE Site_Stack SHALL define no AWS Lambda functions, Amazon API Gateway APIs, or databases of its own, other than the CDK-managed custom-resource functions created internally by `BucketDeployment` and `autoDeleteObjects`.

### Requirement 2: Deploy Script

**User Story:** As a Developer, I want one PowerShell command that builds, checks, and deploys everything, so that every change ships through the same pipeline.

#### Acceptance Criteria

1. THE Deploy_Script SHALL set `$ErrorActionPreference = 'Stop'` and run its steps strictly in the order Scenario_Builder, web build, Secret_Grep, CDK deployment, Smoke_Script, starting each step only after the previous step has succeeded.
2. IF any step fails, including any external command (`python`, `npm`, `npx`, or the Smoke_Script) returning a non-zero exit code, THEN THE Deploy_Script SHALL run no later steps, print an error message naming the failed step, and exit with a non-zero exit code.
3. WHEN the Deploy_Script runs without the `-SkipSim` switch, THE Deploy_Script SHALL run `python -m sim.run_scenarios` as the first step.
4. WHEN the Deploy_Script runs with the `-SkipSim` switch, THE Deploy_Script SHALL skip the Scenario_Builder step and use the existing Scenario_Files without modifying them.
5. IF the Deploy_Script runs with the `-SkipSim` switch and either Scenario_File (`web/public/scenarios/peak.json` or `web/public/scenarios/sun.json`) does not exist, THEN THE Deploy_Script SHALL stop before the web build, print an error message naming each missing Scenario_File, and exit with a non-zero exit code.
6. WHEN the Scenario_Builder step completes successfully or is skipped, THE Deploy_Script SHALL run `npm ci` followed by `npm run build` in `web/`.
7. WHEN `npm run build` completes successfully, THE Deploy_Script SHALL run the Secret_Grep as an exact, case-sensitive match of the EIA_API_KEY value read from `.env` against the contents of every file under `web/dist`, before running any AWS deployment command.
8. IF `.env` does not exist, or does not contain a non-empty EIA_API_KEY value, THEN THE Deploy_Script SHALL stop before any AWS deployment command, print an error message indicating the Secret_Grep cannot run because the key is unavailable, and exit with a non-zero exit code.
9. IF the Secret_Grep finds the EIA_API_KEY value in one or more files under `web/dist`, THEN THE Deploy_Script SHALL stop before any AWS deployment command, print the path of every matching file without printing the key value, and exit with a non-zero exit code.
10. WHEN the Secret_Grep finds no match in any file under `web/dist`, THE Deploy_Script SHALL run `npx cdk deploy --require-approval never` in `infra/`.
11. WHEN the CDK deployment completes successfully, THE Deploy_Script SHALL print the Site_Stack's `SiteUrl` output and then run the Smoke_Script against that Site_URL.
12. WHEN the Smoke_Script exits with a zero exit code, THE Deploy_Script SHALL exit with a zero exit code.

### Requirement 3: Smoke Test Script

**User Story:** As a Developer, I want an automated post-deploy check, so that I know the live site works and the bucket is private.

#### Acceptance Criteria

1. WHEN the Smoke_Script runs against a Site_URL, THE Smoke_Script SHALL send `GET /` to the Site_URL and record the check as passed only if the response status is HTTP 200.
2. WHEN the Smoke_Script runs against a Site_URL, THE Smoke_Script SHALL send `GET /scenarios/peak.json` to the Site_URL and record the check as passed only if the response status is HTTP 200 and the full response body parses as JSON, so that an HTML fallback page returned with status 200 fails the check.
3. WHEN the Smoke_Script runs against a Site_URL, THE Smoke_Script SHALL send an unauthenticated `GET` to the direct S3 object URL of `index.html` in the Site_Bucket and record the check as passed only if the response status is HTTP 403.
4. WHEN the Smoke_Script runs against a Site_URL, THE Smoke_Script SHALL execute all three checks in criteria 1 to 3 regardless of whether an earlier check fails, and print one line per check showing the check name, the observed status, and pass or fail.
5. IF a Smoke_Script request receives no response within 15 seconds or fails with a network error, THEN THE Smoke_Script SHALL record that check as failed with an observed status indicating timeout or network error.
6. IF the Smoke_Script is started without a Site_URL, THEN THE Smoke_Script SHALL print an error message indicating the Site_URL is missing, send no requests, and exit with a non-zero code.
7. IF one or more Smoke_Script checks fail, THEN THE Smoke_Script SHALL print the name and observed status of each failing check and exit with a non-zero code.
8. WHEN all three Smoke_Script checks pass, THE Smoke_Script SHALL print a pass summary showing 3 of 3 checks passed and exit with code 0.

### Requirement 4: Continuous Integration

**User Story:** As a Developer, I want CI on every push, so that tests, the web build, and the CDK synth stay green without AWS credentials.

#### Acceptance Criteria

1. WHEN a commit is pushed to any branch of the GitHub repository, THE CI_Pipeline SHALL start one workflow run for that commit that runs three checks: the Test_Suite via `pytest`, the Web_App build via `npm ci` followed by `npm run build` in `web/`, and `npx cdk synth` in `infra/`.
2. THE CI_Pipeline SHALL complete every check without AWS credentials configured, and SHALL contain no step that runs `cdk deploy`, `cdk bootstrap`, the Deploy_Script, or any other command that writes to an AWS account.
3. THE CI_Pipeline SHALL complete every check without the EIA_API_KEY value configured or referenced, using only files committed to the repository (including the Raw_Cache) as simulation input.
4. WHEN all three checks exit with code 0, THE CI_Pipeline SHALL mark the workflow run for that commit as passed.
5. IF any CI_Pipeline step exits with a non-zero code, including one or more failed Test_Suite tests, a Web_App build error, or a `npx cdk synth` error, THEN THE CI_Pipeline SHALL mark the workflow run for that commit as failed and SHALL report which step failed in the run's output.
6. WHERE the CI_Pipeline is cut for schedule reasons, THE Developer SHALL record the cut as an entry in the Decisions_File and SHALL run `npx cdk synth` locally in `infra/` with exit code 0 before each Deploy_Script run.

### Requirement 6: Secret Handling

**User Story:** As a Developer, I want the EIA API key confined to my local machine, so that the key is never exposed in the public repo, the web bundle, or CDK output.

#### Acceptance Criteria

1. THE EIA_Fetcher SHALL be the only module in the Headroom_System that reads EIA_API_KEY to make EIA API requests, with no file under `web/` or `infra/` reading EIA_API_KEY; the Deploy_Script is the sole exception and SHALL read the EIA_API_KEY value only to perform the Secret_Grep.
2. WHEN the EIA_Fetcher requires an EIA API response that is not present in the Raw_Cache, THE EIA_Fetcher SHALL read EIA_API_KEY at run time from the process environment, and SHALL fall back to the `.env` file at the repository root only if the process environment variable is unset.
3. THE Headroom_System SHALL contain no occurrence of the EIA_API_KEY value, by exact case-sensitive string match, in any git-tracked file of any commit pushed to the public repo, in any file under `web/dist`, or in any file under `infra/cdk.out`.
4. THE Headroom_System SHALL store the EIA_API_KEY value in no environment variable whose name begins with the `VITE_` prefix.
5. THE `.gitignore` file SHALL include entries for `.env`, `node_modules/`, `cdk.out/`, `web/dist/`, `__pycache__/`, and `.venv/`, such that git reports each of those paths as ignored, including `infra/cdk.out/` and `node_modules/` in any subdirectory.
6. THE `.env.example` file SHALL contain exactly one non-empty line, `EIA_API_KEY=`, with no characters after the equals sign.
7. IF a real EIA_API_KEY value is found in any git-tracked file, THEN THE Developer SHALL replace the value with the empty placeholder, commit the fix, and revoke and reissue the key at eia.gov/opendata.
8. IF EIA_API_KEY is unset, empty, or whitespace-only in both the process environment and the `.env` file, and the Raw_Cache lacks a required response, THEN THE EIA_Fetcher SHALL exit with a non-zero code, write no partial file to the Raw_Cache, and print a message naming the missing `EIA_API_KEY` variable without printing any key value.
9. THE EIA_Fetcher SHALL write the EIA_API_KEY value to no Raw_Cache file, standard output, standard error, or error message, including any request URL it prints or stores.
10. IF the Secret_Grep, which the Deploy_Script runs after the web build and before `cdk deploy`, finds the EIA_API_KEY value in any file under `web/dist`, THEN THE Deploy_Script SHALL exit with a non-zero code without running `cdk deploy` and print the path of each matching file without printing the key value.
11. THE CI_Pipeline SHALL complete its pytest, web build, and `cdk synth` steps with no EIA_API_KEY defined in its environment, using only the committed Raw_Cache.

### Requirement 7: EIA Data Ingestion and Caching

**User Story:** As a Developer, I want real EIA-930 data fetched once and cached in the repo, so that builds are reproducible and need no network access.

#### Acceptance Criteria

1. WHEN the EIA_Fetcher runs, THE EIA_Fetcher SHALL request PACE Region_Data from `https://api.eia.gov/v2/electricity/rto/region-data/data/` with `frequency=hourly`, `data[0]=value`, `facets[respondent][]=PACE`, `facets[type][]` values `D`, `DF`, `NG`, and `TI`, sorted by `period` ascending, with `length=5000`.
2. WHEN the EIA_Fetcher runs, THE EIA_Fetcher SHALL request Fuel_Mix_Data from `https://api.eia.gov/v2/electricity/rto/fuel-type-data/data/` for respondents `PACE`, `BPAT`, and `CISO` using the same frequency, value, sort, and length parameters.
3. THE EIA_Fetcher SHALL bound every request so that the earliest requested period is 2026-06-01T00 UTC and the latest requested period is 2026-09-30T23 UTC, matching the Data_Range.
4. WHEN an EIA API response contains exactly `length` (5,000) rows, THE EIA_Fetcher SHALL request the next page with `offset` increased by 5,000, and SHALL stop paginating when a response contains fewer than 5,000 rows, including zero rows.
5. WHEN the EIA_Fetcher receives a successful response, THE EIA_Fetcher SHALL write that response JSON to the Raw_Cache as one cached response per unique combination of endpoint, respondent, type facets, and `offset`, with no rows added, removed, or altered.
6. WHEN the Raw_Cache already holds the cached response for a given combination of endpoint, respondent, type facets, and `offset`, THE EIA_Fetcher SHALL load that cached response and make zero network requests for that combination.
7. THE Raw_Cache SHALL be committed to git so that, with network access disabled and no EIA_API_KEY present, `python -m sim.run_scenarios` exits with code 0 and writes both Scenario_Files.
8. IF the EIA API returns a non-success HTTP status, a response body containing an error, or the request fails to connect, THEN THE EIA_Fetcher SHALL exit with a non-zero code, report the endpoint, the request parameters with the EIA_API_KEY value omitted, and the error message, and write nothing to the Raw_Cache for the failed request.
9. WHEN the Developer changes an EIA endpoint or parameter to fix an API error, THE Developer SHALL record the old value, the new value, and the reason for the change in the Decisions_File.
10. THE EIA_Fetcher SHALL parse each EIA `period` value as a UTC timestamp.
11. THE Web_App SHALL display every timestamp converted to the America/Denver time zone.
12. WHEN the Scenario_Builder converts hourly EIA values to Slots, THE Scenario_Builder SHALL assign each hourly value unchanged to the four Slots that start at minutes :00, :15, :30, and :45 of that hour.
13. IF a Scenario window is missing an hourly EIA value, THEN THE Scenario_Builder SHALL fill each missing hour by linear interpolation between the nearest present values before and after the gap, fill a gap at the start or end of the window with the nearest present value, and record the number of filled hours per series in `meta.params`.
14. IF the EIA_Fetcher needs to make a network request and EIA_API_KEY is absent or empty, THEN THE EIA_Fetcher SHALL exit with a non-zero code before sending any request and report that EIA_API_KEY is missing.
15. THE Raw_Cache SHALL contain no occurrence of the EIA_API_KEY value in any cached file.
16. IF a Scenario window has zero present hourly values for a series the Scenario_Builder requires, THEN THE Scenario_Builder SHALL exit with a non-zero code, name the series and respondent in its report, and write no Scenario_File for that Scenario.

### Requirement 8: Fuel Mapping and Carbon Intensity

**User Story:** As a judge, I want carbon intensity computed transparently from the real fuel mix, so that I can trust the CO₂ numbers and their limits.

#### Acceptance Criteria

1. THE Carbon_Calculator SHALL map Known_Fuel_Codes to Emission_Factor_Table entries as follows: `COL` to Coal, `NG` to Natural gas, `NUC` to Nuclear, `OIL` to Oil, `OTH` to Other, `SUN` to Solar, `WAT` to Hydro, and `WND` to Wind, using the emission factor values read from the Config_Module.
2. IF Fuel_Mix_Data contains a fuel code outside Known_Fuel_Codes, THEN THE Carbon_Calculator SHALL map the code to Other (300 gCO₂eq/kWh) and log one entry per distinct unknown code and respondent, containing the code, the respondent, and the number of rows carrying that code.
3. IF a fuel generation value in Fuel_Mix_Data is negative or missing, THEN THE Carbon_Calculator SHALL treat the value as zero in both the weighted sum and the total generation for that hour.
4. THE Carbon_Calculator SHALL compute one Carbon_Intensity value in gCO₂eq/kWh for each hour of the Data_Range for each of `PACE`, `BPAT`, and `CISO`, equal to the sum over fuels of (generation × emission factor) divided by the sum over fuels of generation.
5. WHEN the Carbon_Calculator computes Carbon_Intensity for an hour with total generation greater than zero, THE Carbon_Calculator SHALL produce a value greater than or equal to the smallest emission factor and less than or equal to the largest emission factor among the fuels with generation greater than zero in that hour.
6. IF an hour has zero total generation, THEN THE Carbon_Calculator SHALL fill that hour by linear interpolation between the nearest preceding and nearest following hours with total generation greater than zero, using the value of the single nearest such hour when the zero-generation hour is at the start or end of the Data_Range, and log the region and UTC timestamp of each filled hour.
7. IF a region has zero total generation in every hour of the Data_Range, THEN THE Carbon_Calculator SHALL stop with an error indicating the region has no usable fuel mix data and SHALL NOT write a Carbon_Intensity series for that region.
8. THE Config_Module SHALL store every Emission_Factor_Table value with a label adjacent to it, labeling Coal, Natural gas, Biomass, Solar, Hydro, Nuclear, Wind, and Geothermal as REAL (IPCC AR5 median) and Oil and Other as ILLUSTRATIVE.
9. THE Web_App SHALL display the text "average intensity, not marginal" within the same panel as every carbon intensity visualization, including the Main_Chart carbon intensity color band, visible without any user interaction.

### Requirement 9: Scenario Window Selection

**User Story:** As a presenter, I want scenario windows chosen from the data, so that the "hot-week peak" and "sunny day" stories are real and not hand-picked.

#### Acceptance Criteria

1. THE Scenario_Selector SHALL select the Peak_Scenario as the 48 consecutive hourly periods that start 24 hours before the hour with the highest PACE `D` value in the Data_Range and end with the hourly period starting 23 hours after that hour, so that the peak hour is the 25th hour of the window and the window contains 192 Slots.
2. IF the Peak_Scenario window from criterion 1 would start before 2026-06-01T00:00Z or end with an hourly period later than 2026-09-30T23:00Z, THEN THE Scenario_Selector SHALL shift the window by the minimum number of whole hours needed to place the window fully inside the Data_Range, keeping the window length at 48 hours and the peak hour inside the window.
3. THE Scenario_Selector SHALL select the Sun_Scenario by evaluating every candidate 48-hour window whose first hourly period starts on a UTC hour from 2026-06-01T00:00Z through 2026-09-29T00:00Z inclusive and choosing the candidate with the highest Solar_Share.
4. IF two or more candidates tie on the selection value (PACE `D` value for the Peak_Scenario peak hour, or Solar_Share for the Sun_Scenario window), THEN THE Scenario_Selector SHALL select the candidate with the earliest UTC start timestamp.
5. WHEN the Scenario_Builder writes a Scenario_File, THE Scenario_Builder SHALL write `meta.window` as two UTC ISO 8601 timestamps: the start of the window's first Slot and the window end, equal to the first Slot start plus 48 hours.
6. WHEN the Scenario_Selector computes Solar_Share for a candidate window, THE Scenario_Selector SHALL treat negative PACE `SUN` values as zero, exclude from both numerator and denominator any hour missing a PACE `SUN` value or a PACE total net generation value, and exclude from selection any candidate whose summed total net generation is zero.
7. IF the Raw_Cache contains no PACE `D` values or no PACE Fuel_Mix_Data values within the Data_Range, THEN THE Scenario_Selector SHALL exit with a non-zero code and a message naming the missing series, and the Scenario_Builder SHALL write no Scenario_File.

### Requirement 10: Simulated Site Model

**User Story:** As a judge, I want the simulated site parameters explicit and labeled, so that I can tell what is real and what is assumed.

#### Acceptance Criteria

1. THE Config_Module SHALL hold every simulation constant listed in this requirement (facility, inference, training, Battery, Flywheel, Tariff, carbon shadow price, and seed), with each constant carrying a comment labeling it REAL or ILLUSTRATIVE, and no other module under `sim/` SHALL redefine any of these constants as a literal value.
2. THE Site_Model SHALL model an IT_Peak of 10,000 kW and a PUE of 1.3, giving a facility peak of 13,000 kW.
3. THE Site_Model SHALL compute facility power in each Slot as IT power (Inference_Load plus running Training_Job load, in kW) multiplied by PUE.
4. THE Site_Model SHALL size Inference_Load so that its maximum value in any Slot equals 3,500 kW (35% of IT_Peak), and THE Job_Generator SHALL set the Training_Job arrival rate so that the expected aggregate Training_Job load (arrival rate × mean job power × mean job duration) equals 6,500 kW (65% of IT_Peak).
5. THE Site_Model SHALL shape Inference_Load with a daily profile that repeats every 24 hours, stays between 0 kW and 3,500 kW in every Slot, and reaches its daily maximum in a Slot starting at or after 12:00 and before 22:00 America/Denver.
6. THE Job_Generator SHALL generate Training_Job arrivals across the full Scenario window as a Poisson process whose random number generator is seeded from the seed value in the Config_Module.
7. THE Job_Generator SHALL assign each Training_Job a power between 50 kW and 800 kW inclusive and a duration between 1 hour and 12 hours inclusive.
8. THE Job_Generator SHALL set each Training_Job deadline to arrival time plus duration plus a slack between 6 hours and 24 hours inclusive.
9. THE Site_Model SHALL allow a Training_Job to pause and resume only at Slot boundaries.
10. WHEN a paused Training_Job resumes, THE Site_Model SHALL add one Restart_Penalty (5 minutes) to that Training_Job's remaining run time, so that the Training_Job's total delivered energy equals its power multiplied by (duration plus 5 minutes per resume).
11. THE Site_Model SHALL model the Battery with a charge and discharge power limit of 4,000 kW, an energy capacity of 16,000 kWh, and 90% round-trip efficiency, such that energy discharged over a full charge–discharge cycle equals 90% of the energy drawn for charging.
12. THE Site_Model SHALL model the Flywheel with a charge and discharge power limit of 2,000 kW, an energy capacity of 500 kWh, and 85% round-trip efficiency, such that energy discharged over a full charge–discharge cycle equals 85% of the energy drawn for charging.
13. THE Site_Model SHALL start each Scenario with the Battery SOC and the Flywheel SOC at initial values defined in the Config_Module between 10% and 95%, and SHALL keep both SOC values between 10% and 95% inclusive in every Slot and every Event_Zoom second.
14. THE Site_Model SHALL limit each storage device to exactly one of charging, discharging, or idle in any single Slot or Event_Zoom second.
15. THE Site_Model SHALL keep Site_Grid_Draw at or above 0 kW in every Slot and every Event_Zoom second.
16. THE Tariff SHALL charge $0.085/kWh for Site_Grid_Draw energy in Slots starting at or after 15:00 and before 20:00 America/Denver, Monday through Friday (the On_Peak_Period), and $0.045/kWh in all other Slots, with both rates labeled ILLUSTRATIVE and not Rocky Mountain Power's actual rates.
17. THE Tariff SHALL apply a demand charge of $18/kW to the highest 15-minute Site_Grid_Draw in the Scenario window, computed separately for each policy, used as the proxy for the monthly peak.
18. THE Config_Module SHALL set the carbon shadow price to $50 per tonne CO₂eq, labeled ILLUSTRATIVE.
19. WHEN the Job_Generator runs twice with the same seed, THE Job_Generator SHALL produce identical Training_Job lists, with every Training_Job matching in id, arrival time, power, duration, and deadline, in the same order.
20. IF a Training_Job has not completed its full run time (including Restart_Penalties) by its deadline, THEN THE Site_Model SHALL flag that Training_Job as having missed its deadline.

### Requirement 11: Scheduling Policies

**User Story:** As a presenter, I want a baseline policy and a Headroom policy with the same interface, so that toggling between them shows exactly what flexibility buys.

#### Acceptance Criteria

1. THE Scheduler SHALL expose the Baseline_Policy and the Headroom_Policy through one interface that takes the same Scenario inputs (the Scenario's 192 Slots of grid data, the Training_Job list, and the Config_Module constants) and returns the same output structure: one per-Slot power entry for each of the 192 Slots and a list of Decisions.
2. THE Baseline_Policy SHALL run every Training_Job continuously from its arrival Slot until completion using grid power, with no pauses, no deferral, no region moves, and zero Battery and Flywheel charge or discharge in every Slot.
3. THE Headroom_Policy SHALL plan each Slot with a rolling look-ahead window covering the current Slot and the following 95 Slots (24 hours), truncated at the last Slot of the Scenario window.
4. WHEN the Headroom_Policy evaluates Slots in the look-ahead window, THE Headroom_Policy SHALL use PACE `DF` forecast demand, Carbon_Intensity, and the Tariff as planning inputs, and SHALL NOT use PACE `D` actual demand values for Slots later than the current Slot.
5. WHEN a Slot begins, THE Headroom_Policy SHALL assign exactly one Route (`GRID_NOW`, `STORAGE_NOW`, `DEFER`, or `MOVE_REGION`) to each runnable Training_Job, where a runnable Training_Job is one whose arrival time is at or before the Slot start and whose remaining run time is greater than zero, and SHALL emit Decisions as specified in Requirement 13.
6. WHEN the Headroom_Policy assigns `DEFER`, THE Headroom_Policy SHALL record a target Slot that is later than the current Slot, lies within the current look-ahead window, and leaves the Training_Job able to finish by its deadline including one added Restart_Penalty.
7. THE Headroom_Policy SHALL compute a Route_Cost for each candidate Route available to a Training_Job in the current Slot and assign the candidate with the lowest Route_Cost.
8. WHEN two or more candidate Routes have equal Route_Cost, THE Headroom_Policy SHALL break the tie in the fixed order `GRID_NOW`, `STORAGE_NOW`, `DEFER`, `MOVE_REGION`, choosing the earliest Route in that order.
9. IF every candidate Route except `GRID_NOW` would put a Training_Job's deadline at risk, where a Route puts the deadline at risk when the job's projected finish time under that Route (remaining run time, plus one Restart_Penalty per pause, plus the 30-minute delay for `MOVE_REGION`) is later than the job's deadline, THEN THE Headroom_Policy SHALL assign `GRID_NOW` to that Training_Job.
10. THE Headroom_Policy SHALL schedule Inference_Load at kW values identical to the Baseline_Policy's in every Slot of the Scenario, with no Inference_Load deferred or moved to an Alternate_Region.
11. THE Headroom_Policy SHALL complete every Training_Job by the Training_Job's deadline.
12. IF a Training_Job finishes after the Training_Job's deadline, THEN THE Scheduler SHALL flag the Training_Job as late in the Decisions and count the Training_Job as missed in the deadlines met metric.
13. THE Headroom_Policy SHALL charge storage only in the Slots of the look-ahead window that rank lowest by energy price plus Carbon_Intensity multiplied by the carbon shadow price, and only when the charging would not raise the window's peak Site_Grid_Draw and the Slot is outside a DR_Event.
14. WHEN a Slot's Site_Grid_Draw before storage discharge would exceed the highest Site_Grid_Draw already planned for the Scenario window, THE Headroom_Policy SHALL discharge the Battery and Flywheel, within each device's power rating and above its 10% SOC floor, to reduce that Slot's Site_Grid_Draw.
15. WHILE a DR_Event is active, THE Headroom_Policy SHALL discharge storage so that Site_Grid_Draw stays at or below the Grid_Import_Cap in every Slot and every Event_Zoom second.
16. IF the combined available discharge power of the Battery and Flywheel in a Slot, limited by each device's power rating and 10% SOC floor, is less than a Training_Job's power, THEN THE Headroom_Policy SHALL exclude `STORAGE_NOW` from that Training_Job's candidate Routes for that Slot.
17. THE Scheduler SHALL implement the Headroom_Policy as a greedy algorithm that assigns each Slot's Routes from that Slot's Route_Costs without revising Decisions already made for earlier Slots, favoring transparent Reason_Strings over optimality.
18. IF the greedy Headroom_Policy fails acceptance criterion 23.6, THEN THE Developer SHALL replace the greedy algorithm with a linear program (`pulp`) and record the reason in the Decisions_File.

### Requirement 12: MOVE_REGION Route

**User Story:** As a judge, I want moving work to another region to carry realistic costs, so that geographic shifting is not presented as free.

#### Acceptance Criteria

1. WHERE the `MOVE_REGION` route is enabled, THE Headroom_Policy SHALL offer `MOVE_REGION` only to Training_Jobs (never to Inference_Load) and only with `BPAT` or `CISO` as the target Alternate_Region.
2. WHERE the `MOVE_REGION` route is enabled, THE Headroom_Policy SHALL add a fixed transfer penalty in US dollars, defined once in the Config_Module and labeled ILLUSTRATIVE, to the `MOVE_REGION` Route_Cost exactly once per moved Training_Job, independent of the job's power or duration.
3. WHERE the `MOVE_REGION` route is enabled, WHEN the Headroom_Policy assigns `MOVE_REGION` to a Training_Job in a Slot, THE Headroom_Policy SHALL start that Training_Job in the target Alternate_Region 30 minutes (2 Slots) after that Slot.
4. WHERE the `MOVE_REGION` route is enabled, THE Site_Model SHALL simulate Idle_Capacity for each Alternate_Region for each hour of the Scenario as a value between 0% and 30% inclusive, expressed in kW as that percentage of IT_Peak, generated from the Scenario seed so that the same seed produces identical Idle_Capacity values on every run.
5. IF a Training_Job's power exceeds the remaining Idle_Capacity of the target Alternate_Region in any hour the moved job would run there, where remaining Idle_Capacity equals the hour's Idle_Capacity minus the power of Training_Jobs already moved to that Alternate_Region for that hour, THEN THE Headroom_Policy SHALL reject the `MOVE_REGION` Route for that Training_Job and assign the next-lowest-cost Route among `GRID_NOW`, `STORAGE_NOW`, and `DEFER`.
6. WHERE the `MOVE_REGION` route is enabled, THE Metrics_Calculator SHALL exclude a moved Training_Job's power from Site_Grid_Draw for the Slots it runs in the Alternate_Region and SHALL account that job's energy at the target Alternate_Region's hourly Carbon_Intensity for each hour it runs there.
7. IF the 30-minute delay plus a Training_Job's remaining duration would place its completion after its deadline, THEN THE Headroom_Policy SHALL reject the `MOVE_REGION` Route for that Training_Job and assign the next-lowest-cost Route among `GRID_NOW`, `STORAGE_NOW`, and `DEFER`.
8. WHEN the Headroom_Policy assigns `MOVE_REGION` to a Training_Job, THE Headroom_Policy SHALL emit a Decision whose Reason_String names the target Alternate_Region, the transfer penalty in dollars, the 30-minute delay, and the target region's Carbon_Intensity for the start hour.
9. WHERE the `MOVE_REGION` route is disabled, THE Headroom_Policy SHALL emit zero Decisions with Route `MOVE_REGION` and SHALL assign routes only from `GRID_NOW`, `STORAGE_NOW`, and `DEFER`.

### Requirement 13: Decision Reasons

**User Story:** As a presenter, I want every scheduling decision explained in plain language, so that the audience sees why each job went where it went.

#### Acceptance Criteria

1. WHEN the Headroom_Policy assigns a Route to a Training_Job in a Slot that differs from the Route assigned to that Training_Job in the previous Slot, THE Scheduler SHALL emit exactly one Decision for that Training_Job in that Slot.
2. WHEN the Headroom_Policy assigns a Route to a Training_Job for the first time in a Scenario, THE Scheduler SHALL emit exactly one Decision for that Training_Job in that Slot.
3. THE Scheduler SHALL include in every Reason_String, in this order: the Slot start time as 24-hour `HH:MM` in America/Denver, the job id prefixed with `job#`, the Route, the target when present, the PACE demand percentile, the Carbon_Intensity in g/kWh, and the Demand_Charge_Risk peak change in kW.
4. THE Scheduler SHALL format Reason_Strings in the style `14:15 job#4412 → DEFER to 01:00 — PACE demand 97th pct, 610 g/kWh, would raise monthly peak by 380 kW`, where the PACE demand percentile is the percentage of the Scenario's 192 Slots whose PACE demand is less than or equal to the Slot's PACE demand, rounded down to an integer from 1 to 100 with an English ordinal suffix; the Carbon_Intensity is rounded to the nearest integer; and the peak change is a non-negative integer in kW, with 0 kW stated when the Route does not raise the peak.
5. THE Scheduler SHALL set the Reason_String target to `to HH:MM` (the America/Denver start time of the Slot in which the Training_Job resumes) for the `DEFER` Route, to `to BPAT` or `to CISO` for the `MOVE_REGION` Route, and SHALL omit the target for the `GRID_NOW` and `STORAGE_NOW` Routes.
6. WHILE a DR_Event is active, WHEN a Training_Job's Route changes because of the DR_Event, THE Scheduler SHALL emit a Decision for that Training_Job whose Reason_String, in addition to the content in criterion 3, identifies the DR_Event as the cause and states the Grid_Import_Cap in kW.
7. IF a Training_Job's Route in a Slot is the same as its Route in the previous Slot, THEN THE Scheduler SHALL NOT emit a Decision for that Training_Job in that Slot.
8. THE Scheduler SHALL record in each Decision a time equal to the Slot start time, plus a job id, Route, and target that match the job id, Route, and target stated in that Decision's Reason_String.
9. THE Scheduler SHALL keep every Reason_String to 200 characters or fewer.

### Requirement 14: Demand-Response Event

**User Story:** As a presenter, I want to fire a demand-response event and show the site hitting the cap within seconds, so that the audience sees storage acting as a grid asset.

#### Acceptance Criteria

1. THE Scenario_Builder SHALL simulate exactly one DR_Event per Scenario, with a Requested_Shed of 4,000 kW, a duration of 2 hours (8 consecutive Slots), and a Battery ramp time of 20 seconds, all three values read from the Config_Module.
2. THE Scenario_Builder SHALL start the DR_Event at the beginning of the Slot with the highest PACE demand among the Slots whose 8-Slot event span lies entirely within the Scenario window, choosing the earliest such Slot when demand values tie, and SHALL set the DR_Event end to the start time plus 2 hours.
3. THE Scenario_Builder SHALL set `requested_shed_kw` to the Requested_Shed and `cap_kw` to the Grid_Import_Cap, computed from the Baseline_Policy Site_Grid_Draw in the DR_Event start Slot.
4. WHILE a DR_Event is active, from its start Slot through its 8th Slot inclusive, THE Headroom_Policy SHALL hold Site_Grid_Draw at or below `cap_kw` in every Slot without exceeding 4,000 kW Battery discharge or 2,000 kW Flywheel discharge.
5. THE Scenario_Builder SHALL generate the Event_Zoom as exactly 600 entries with `s` values 0 through 599 in one-second steps starting at the DR_Event start, where in every entry `grid_kw` + `flywheel_kw` + `battery_kw` equals the Headroom_Policy site load of the DR_Event start Slot, and the required storage output equals that site load minus `cap_kw`, or 0 kW if the site load is at or below `cap_kw`.
6. WHEN the DR_Event starts, THE Site_Model SHALL set `battery_kw` to 0 kW and `flywheel_kw` to the full required storage output in the Event_Zoom entry with `s` = 0.
7. WHEN the DR_Event starts, THE Site_Model SHALL increase `battery_kw` linearly from 0 kW at `s` = 0 to the full required storage output at `s` = 20 and hold it there through `s` = 599, and SHALL set `flywheel_kw` in each entry to the required storage output minus `battery_kw`, reaching 0 kW at `s` = 20.
8. THE Site_Model SHALL keep `grid_kw` at or below `cap_kw`, `flywheel_kw` between 0 and 2,000 kW, and `battery_kw` between 0 and 4,000 kW in every Event_Zoom entry.
9. THE Metrics_Calculator SHALL report `dr_delivered_pct` as the Baseline_Policy Site_Grid_Draw in the DR_Event start Slot minus the maximum Headroom_Policy Site_Grid_Draw across the 8 DR_Event Slots, divided by Requested_Shed, multiplied by 100, and rounded to 1 decimal place.
10. THE Metrics_Calculator SHALL report `dr_seconds_to_full` as the smallest Event_Zoom `s` value at which `flywheel_kw` is 0 kW and `battery_kw` equals the required storage output, as an integer from 0 to 599.
11. IF any DR_Event Slot has Headroom_Policy Site_Grid_Draw above `cap_kw`, or any Event_Zoom entry would need more than 2,000 kW from the Flywheel or more than 4,000 kW from the Battery to keep `grid_kw` at or below `cap_kw`, THEN THE Scenario_Builder SHALL exit with a non-zero status and an error message naming the Scenario and the first violating Slot or second, and SHALL leave that Scenario_File unwritten.

### Requirement 15: Metrics

**User Story:** As a judge, I want headline KPIs that quantify the benefit, so that the insight is clear and measurable.

#### Acceptance Criteria

1. WHEN the Scenario_Builder runs, THE Metrics_Calculator SHALL compute headroom returned (kW) for each Scenario as the maximum Baseline_Policy Site_Grid_Draw across that Scenario's Stress_Slots minus the maximum Headroom_Policy Site_Grid_Draw across the same Stress_Slots.
2. WHEN the Scenario_Builder runs, THE Metrics_Calculator SHALL compute $ saved for each Scenario as the Baseline_Policy's total cost minus the Headroom_Policy's total cost. Each policy's total cost is the sum over all 192 Slots of Site_Grid_Draw (kW) × 0.25 h × the Tariff energy rate for that Slot (on-peak rate in On_Peak_Period Slots, off-peak rate otherwise), plus the policy's peak 15-minute Site_Grid_Draw over the Scenario window × the Tariff demand charge ($/kW), plus, for the Headroom_Policy only, the transfer penalty for each successful MOVE_REGION Decision.
3. WHEN the Scenario_Builder runs, THE Metrics_Calculator SHALL compute CO₂ avoided in tonnes for each Scenario as the Baseline_Policy's emissions minus the Headroom_Policy's emissions. Each policy's emissions are the sum over all 192 Slots of Site_Grid_Draw (kW) × 0.25 h × the PACE Carbon_Intensity for the hour containing that Slot, plus, for MOVE_REGION Decisions, the moved energy (kWh) × the target Alternate_Region's Carbon_Intensity for the matching hour, converted from grams to tonnes by dividing by 1,000,000.
4. WHEN the Scenario_Builder runs, THE Metrics_Calculator SHALL compute training deadlines met for each Scenario as the number of the Headroom_Policy's Training_Jobs that receive their full requested run time plus all Restart_Penalties at or before their deadline, divided by the total number of Training_Jobs generated for that Scenario, expressed as a percentage from 0 to 100.
5. WHEN the Scenario_Builder runs, THE Metrics_Calculator SHALL compute inference SLA for each Scenario as the number of Slots in which the Headroom_Policy's delivered inference power equals the Inference_Load for that Slot, divided by 192, expressed as a percentage from 0 to 100.
6. THE Metrics_Calculator SHALL report an inference SLA value of exactly 100 in the metrics of both the `peak` and `sun` Scenario_Files.
7. THE Metrics_Calculator SHALL report headroom returned, $ saved, and CO₂ avoided as computed, including zero or negative values, and SHALL NOT clamp, omit, or substitute any of them.
8. THE Footer SHALL display the Duke_Context_Line with its source attribution (Duke Nicholas Institute, *Rethinking Load Growth*, Feb 2025), labeled as national planning context, and placed outside the KPI_Row.
9. THE README SHALL include the Duke_Context_Line with its source attribution, presented as national planning context and contain no statement that attributes the 76 GW or 0.25% figures to the simulated site.
10. IF the computed inference SLA for any Scenario is below 100%, THEN THE Scenario_Builder SHALL exit with a non-zero status, identify the failing Scenario, and leave the existing Scenario_Files unchanged.

THE Scenario_Builder SHALL write `dr_event` with exactly the keys `start` and `end` (UTC ISO 8601 Slot times within `meta.window`, with `start` earlier than `end`), `requested_shed_kw` (the Requested_Shed, default 4000), `cap_kw` (the Grid_Import_Cap), and `zoom` (an array of exactly 600 entries ordered by `s` from 0 to 599 in 1-second steps, each with exactly the keys `s`, `grid_kw`, `flywheel_kw`, and `battery_kw` as JSON numbers).

THE Scenario_Builder SHALL write `metrics` with exactly the keys `headroom_kw`, `usd_saved`, `co2_avoided_t`, `deadlines_met_pct`, `inference_sla_pct`, `dr_delivered_pct`, and `dr_seconds_to_full`, each as a JSON number, where every `_pct` value is between 0 and 100 inclusive and `dr_seconds_to_full` is between 0 and 600 inclusive.
11. THE Scenario_Builder SHALL write every `t`, `start`, `end`, `window`, `built_at`, and timestamp-valued `target` in UTC ISO 8601 format with a `Z` suffix (for example `2026-07-15T21:00:00Z`).
12. THE Type_Definitions SHALL mirror the Output_Contract exactly, with matching key names, nesting, value types (number, string, boolean, null, array, object), and the `route` and `scenario` value sets defined in criteria 3 and 8.
13. WHEN the Scenario_Builder runs twice with the same seed, the same Raw_Cache contents, and the same Config_Module values, THE Scenario_Builder SHALL produce Scenario_Files that are byte-identical after excluding the `meta.built_at` value.
14. THE Scenario_Builder SHALL serialize Scenario objects such that parsing a written Scenario_File yields an object equal to the in-memory Scenario object it was written from, with identical key names, nesting, value types, and numeric values (round-trip property).
15. IF the Scenario_Builder cannot produce a Scenario_File that conforms to criteria 2 through 11 (including when required input data is missing from the Raw_Cache), THEN THE Scenario_Builder SHALL exit with a non-zero status, print an error message naming the failing Scenario and the reason, and leave no partially written Scenario_File at the Scenario_File path.

WHILE the Mode is Baseline, THE KPI_Row SHALL display 0 for headroom kW returned, $ saved, and CO₂ avoided, and the Baseline_Policy values for inference SLA and training deadlines met, which are 100% for inference SLA (the Baseline_Policy serves the full Inference_Load from the grid) and 100% for training deadlines met (the Baseline_Policy runs every Training_Job from its arrival Slot without pausing).
8. THE Web_App SHALL make every toggle and button reachable with the Tab key, activatable with the Enter key and the Space key, show a visible focus indicator on the focused control, label every control with a name readable by screen readers, and expose each toggle's selected option to screen readers.
9. WHEN the presenter changes the Mode toggle, THE Web_App SHALL, within 500 milliseconds and without any network request, update the KPI_Row, Main_Chart, and Decision_Log to the selected Mode while keeping the selected Scenario unchanged.
10. THE KPI_Row SHALL format headroom kW returned as a whole number with thousands separators followed by "kW", $ saved as whole US dollars prefixed with "$" and with thousands separators, CO₂ avoided in tonnes rounded to one decimal place followed by "t", and inference SLA and training deadlines met as whole percentages rounded down followed by "%", with a leading minus sign for any negative value.

### Requirement 19: Main Chart

**User Story:** As a presenter, I want one chart that contrasts baseline and Headroom grid draw against the grid's own peak, so that the flattening is obvious at a glance.

#### Acceptance Criteria

1. THE Main_Chart SHALL plot all 192 Slots of the selected Scenario in chronological order on a single time axis, with time-axis labels in America/Denver local time in 24-hour HH:MM format and at least one labeled tick every 6 hours.
2. WHILE the Mode is Baseline, THE Main_Chart SHALL plot the Baseline_Policy Site_Grid_Draw for each Slot as a solid line on a primary axis labeled in kW, and SHALL NOT display the Headroom_Policy Site_Grid_Draw line or the stacked supply areas.
3. WHILE the Mode is Headroom, THE Main_Chart SHALL plot the Headroom_Policy Site_Grid_Draw for each Slot as a solid line and the Baseline_Policy Site_Grid_Draw for each Slot as a ghost line drawn dashed and at lower opacity than the solid line, both on the same primary axis labeled in kW.
4. WHILE the Mode is Headroom, THE Main_Chart SHALL display, for each Slot, stacked supply areas for grid, battery, flywheel, and moved power, in that bottom-to-top order, where each area's height equals that Slot's corresponding kW value in the Headroom_Policy series of the selected Scenario_File.
5. THE Main_Chart SHALL plot PACE demand for each Slot on a secondary axis labeled in MW, independent of the Mode.
6. THE Main_Chart SHALL shade the full chart height for exactly the time span of each Stress_Slot in the selected Scenario, and SHALL leave all non-Stress_Slots unshaded.
7. THE Main_Chart SHALL display Carbon_Intensity as a color band along the time axis, colored per hour on a continuous scale between the selected Scenario's minimum and maximum Carbon_Intensity, with a legend showing those minimum and maximum values in gCO₂eq/kWh and stating "average intensity, not marginal".
8. THE Main_Chart SHALL distinguish every plotted series by line style or fill pattern in addition to color, such that no two series share both the same color and the same line style or pattern.
9. THE Main_Chart SHALL display a legend that names each currently visible series and states its unit (kW for site series, MW for PACE demand).
10. WHEN the presenter switches the Mode or the selected Scenario, THE Main_Chart SHALL redraw with the series for the new selection without making a network request.

### Requirement 20: Demand-Response Button and Zoom Panel

**User Story:** As a presenter, I want a button that fires the demand-response event and animates the response, so that the audience watches the flywheel and battery take over in real time.

#### Acceptance Criteria

1. THE Web_App SHALL display the DR_Button labeled "Fire demand-response event" in both Modes and for both Scenarios.
2. WHILE the Mode is Baseline, THE Web_App SHALL disable the DR_Button, start no Event_Zoom playback when the DR_Button is clicked or keyboard-activated, and show the text "Switch to Headroom to dispatch storage" next to the DR_Button.
3. WHEN the presenter activates the DR_Button while the Mode is Headroom, THE Zoom_Panel SHALL animate the selected Scenario's 600 Event_Zoom entries for `grid_kw`, `flywheel_kw`, and `battery_kw` in order of `s` from 0 to 599, advancing 60 Event_Zoom seconds per elapsed real second, so that the last entry is drawn 10 seconds (±0.5 seconds) after activation.
4. WHEN the presenter activates the DR_Button while the Mode is Headroom, THE Zoom_Panel SHALL draw the selected Scenario's `cap_kw` value as a horizontal reference line for the whole playback, on an x-axis showing seconds from DR_Event start (0 to 599) and a y-axis in kW.
5. WHEN the Event_Zoom playback completes, or the static Event_Zoom chart is shown under criterion 7 or 8, THE KPI_Row SHALL display the selected Scenario's `requested_shed_kw`, `dr_delivered_pct` as the DR delivered percentage, and `dr_seconds_to_full` as the seconds to full response; before then, THE KPI_Row SHALL not display these values.
6. WHEN the presenter activates the DR_Button while the Mode is Headroom, THE Decision_Log SHALL show the DR_Event Decisions at the top of the feed, ordered newest first by `t`. A DR_Event Decision is any Decision whose `t` falls between the selected Scenario's `dr_event.start` and `dr_event.end`, inclusive.
7. WHERE the operating system or browser reports a reduced-motion preference, WHEN the presenter activates the DR_Button while the Mode is Headroom, THE Zoom_Panel SHALL draw all 600 Event_Zoom entries and the `cap_kw` reference line at once, with no animation.
8. WHERE the animated Event_Zoom has been cut under the Requirement 24 cut order, WHEN the presenter activates the DR_Button while the Mode is Headroom, THE Zoom_Panel SHALL show a static chart of all 600 Event_Zoom entries for `grid_kw`, `flywheel_kw`, and `battery_kw` with the `cap_kw` reference line.
9. WHILE the Event_Zoom animation is playing, THE Web_App SHALL ignore further DR_Button activations; WHEN the presenter activates the DR_Button after playback has completed, THE Zoom_Panel SHALL replay the animation from `s` = 0.
10. IF the presenter changes the Mode or the Scenario while the Event_Zoom animation is playing, THEN THE Web_App SHALL stop the animation, clear the Zoom_Panel series, and remove the DR values from the KPI_Row until the DR_Button is activated again.

### Requirement 21: Decision Log

3. THE Decision_Log SHALL color-code each Decision with one distinct color per Route (four colors for `GRID_NOW`, `STORAGE_NOW`, `DEFER`, and `MOVE_REGION`), apply the same Route-to-color mapping to every entry in both Scenarios, and display the Route name as text next to the color.
4. THE Decision_Log SHALL keep a fixed height that does not change as Decisions are added, and SHALL scroll vertically within that height when the Decisions exceed the visible area.
5. WHILE the Mode is Baseline, THE Decision_Log SHALL display only the text "Baseline: every job runs on arrival from the grid." and SHALL list no Decisions.
6. WHEN the user switches the selected Scenario, THE Decision_Log SHALL replace the listed Decisions with the newly selected Scenario's Decisions and scroll to the newest entry at the top.
7. IF the selected Scenario_File's `decisions` array is empty while the Mode is Headroom, THEN THE Decision_Log SHALL display a message saying no Decisions exist for the Scenario, in place of an empty list.

### Requirement 23: Automated Acceptance Tests

**User Story:** As a Developer, I want the core invariants tested automatically, so that the story cannot silently break.

#### Acceptance Criteria

1. THE Test_Suite SHALL verify, for both the Peak_Scenario and the Sun_Scenario, that the `baseline` and `headroom` arrays each contain 192 entries with matching `t` values and that the `inference_kw` value of every `headroom` entry is exactly equal to the `inference_kw` value of the `baseline` entry with the same `t`.
2. THE Test_Suite SHALL verify, for both Scenarios under the Headroom_Policy, that the Battery SOC and the Flywheel SOC are each at least 10% and at most 95% (inclusive) in every one of the 192 Slots, and that neither the Battery nor the Flywheel has both a charge power greater than 0 kW and a discharge power greater than 0 kW in the same Slot.
3. THE Test_Suite SHALL verify, for every completed Training_Job under both policies in both Scenarios, that the job's delivered energy (kWh) is within 0.01 kWh of the job's requested energy (power in kW × duration in hours) plus the job's Restart_Penalty energy (power in kW × 5/60 hours × the number of times the job resumed after a pause).
4. THE Test_Suite SHALL verify, for both policies in both Scenarios, that every Training_Job whose finish time is later than the job's deadline is flagged as late in the Decisions and counted as missed in `metrics.deadlines_met_pct`, and that no Training_Job finishing at or before its deadline is flagged as late.
5. THE Test_Suite SHALL verify, for both Scenarios, that `dr_event.zoom` contains 600 entries with `s` values 0 through 599 and that `grid_kw` is less than or equal to `dr_event.cap_kw` in every one of those entries.
6. THE Test_Suite SHALL verify, for each Scenario, that at least one Slot has `grid.stress` equal to true and that the maximum Headroom_Policy `grid_kw` over the Stress_Slots is strictly less than the maximum Baseline_Policy `grid_kw` over the same Stress_Slots, failing the test when the two values are equal.
7. IF the stress-hour peak test in criterion 6 fails for either Scenario, THEN THE Developer SHALL fix the Scheduler and make no further Web_App changes until criterion 6 passes for both Scenarios.
8. THE Test_Suite SHALL verify that two Scenario_Builder runs using the same seed and the same Raw_Cache produce Scenario_Files that are byte-identical for both `peak.json` and `sun.json` once the `meta.built_at` value is excluded from the comparison.
9. THE Test_Suite SHALL verify that each Scenario_File conforms to the Output_Contract, including exactly the seven required top-level keys, the exact key set of every `meta`, `grid`, `baseline`, `headroom`, `decisions`, `dr_event`, `zoom`, and `metrics` object, 192 entries in each of `grid`, `baseline`, and `headroom`, and UTC ISO 8601 format for every `t`, `start`, `end`, and `window` timestamp.
10. THE Test_Suite SHALL read grid data only from the Raw_Cache and SHALL fail any test that attempts a network connection.
11. IF a Raw_Cache file required by the Test_Suite is missing or unreadable, THEN THE Test_Suite SHALL fail with an error message identifying the missing file and SHALL NOT fetch the data from the EIA API.
12. IF any check in criteria 1 through 9 fails, THEN THE Test_Suite SHALL exit with a non-zero status and report the name of each failing test and the Scenario in which it failed.

### Requirement 24: Scope Constraints and Priorities

**User Story:** As a Developer, I want explicit non-goals and a cut order, so that I protect the demo-critical features when time runs short.

#### Acceptance Criteria

1. THE Headroom_System SHALL be served only as static files from the Site_Bucket through the Distribution, with no Lambda function code authored in the `headroom` repository, no API Gateway, no database, no Serverless Framework, and no authentication of its own (handlers that AWS CDK v2 generates for its own constructs do not count as Lambda functions of the Headroom_System).
2. THE Web_App SHALL obtain all grid, carbon, site, and Decision data from Scenario_Files, making zero network requests to the EIA API at runtime and zero network requests of any kind after the Scenario_Files finish loading.
3. THE Headroom_System SHALL present emissions only as average Carbon_Intensity, and every Web_App view and README section that shows Carbon_Intensity or CO₂ avoided SHALL label the value as average intensity, not marginal, with no marginal-emissions claims anywhere in the Web_App or README.
4. THE Site_Model SHALL represent each Training_Job only as a synthetic power profile defined by its power (kW), duration, arrival time, and deadline, with no ML training performed by any part of the Headroom_System.
5. IF a milestone deliverable listed in `AGENT_BRIEF_HEADROOM.md` is incomplete at the end time of its milestone window (Mountain Time, Tuesday Oct 27, 2026), THEN THE Developer SHALL cut exactly one scope item at a time, in this order, never cutting a later item while an earlier item remains: (1) the CI_Pipeline (keeping a local `npx cdk synth` that succeeds), (2) the Sun_Scenario, (3) the `MOVE_REGION` Route, (4) the animated Event_Zoom (keeping a static event chart), and SHALL record each cut with its time and reason in the Decisions_File.
6. THE Headroom_System SHALL include the live Site_URL, real PACE data, the baseline vs Headroom Main_Chart, the KPI_Row, the Decision_Log, and the REAL/ILLUSTRATIVE/SIMULATED labels in the build deployed at feature freeze (Oct 27, 2026, 10 PM MT) and in every later deployment, and no scope cut under criterion 5 SHALL remove any of these items.
7. WHERE the Sun_Scenario is cut, THE Web_App SHALL hide the Scenario toggle and THE Scenario_Builder SHALL write only `peak.json`.
8. WHERE the `MOVE_REGION` Route is cut, THE Scheduler SHALL assign only `GRID_NOW`, `STORAGE_NOW`, or `DEFER` Routes, and no Scenario_File SHALL contain a Decision with the `MOVE_REGION` Route.
9. WHERE the animated Event_Zoom is cut, THE Web_App SHALL display the Event_Zoom series as a static chart covering all 600 seconds when the DR_Button is pressed, with no animated playback.
